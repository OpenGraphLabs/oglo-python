# 0.9.16 현장 녹화 USB 실패 검수 — 2026-09-20

> Historical validation record for the dated software and devices below.
> See [current candidate status](../08_candidate_status.md) before choosing a release.
> Raw `acceptance-results/` paths identify internally retained evidence, not public downloads.

**현장 녹화에서도 USB 수신 실패와 재연결 실패가 실제로 발생했다.**
시험 녹화 1개를 제외한 업로드 녹화 554개(151.662시간) 중 51개에서 녹화 시간
안의 장갑 USB reader 실패를 확인했다. 그중 49개는 촉각 RAW가 먼저 끝나고
카메라 프레임 기록이 5초 이상 이어지는 사실까지 확인했다.
**이 51개가 모두 이번 FIFO 배정 결함 때문에
실패했는지는 미확정이다.** 과거 실행 이미지 해시, FIFO 레지스터, USB 전송
추적과 당시 케이블 조작 기록이 없어 개별 사건의 최초 원인까지 확정할 수 없다.

새로 연결한 세 번째 장갑도 동일한 SDK 없는 비교 검사에서 두 번 모두 수신이
멈췄다. 세 장갑의 현재 실행 펌웨어 해시는 동일하다. FIFO 수정 개입 검사는
여전히 첫 장갑 한 대에서만 수행했다.

## 검수 범위와 방법

- 9월 20일 GCS를 새로 조회했다. 메타데이터 수집 시각은 14:31:05–14:31:39 KST다.
  `opengraph-raw` 및 `opengraph-raw-uss1`의 `opengraph/setup=*tactile/**`를
  페이지 끝까지 조회했다. 주 버킷에서 관련 객체 11,414개와 녹화 경로 1,385개를
  찾았으며, 두 번째 버킷에는 해당 객체가 없었다. 두 버킷 전체의 calibration
  경로도 확인했으며, 주 경로 밖의 14개는 명시적인 `test-sandbox` 자료였다.
- 장갑은 calibration의 `device_id`, serial, `fw_rev`로 식별했다. Pi는
  `ogskill_session.json`에서 식별하고 manifest와 대조했다. 녹화 ID는 session과
  collection segment에서 대조했다. 과거의 `fw_rev=0.9.16`은 **저장된 버전
  표기**이며, 현재 벤치 장갑과 같은 바이너리라는 해시 증거는 없다.
- 0.9.16 표기가 있는 녹화는 555개였다. `site_id=bench` /
  `sdk_version=benche2e`로 표시된 시험 녹화 1개를 제외했다. 일반 보고서가 있는
  **512개, 양손 스트림 1,024개, 136.434시간**과 중단 후 복구된
  **42개, 대상 손별 스트림 83개, 15.228시간**을 별도로 검사한 뒤 합산했다.
  복구 녹화 1개는 반대 손의 FW 버전이 달라 대상 손이 한 개다. 녹화의 실제 현장
  작업 여부를 영상 내용이나 작업자에게 재확인한 것은 아니다.
- 기간은 2026-08-17 16:47:37부터 2026-09-19 17:15:38 KST까지이며,
  Pi 10대와 물리 장갑 ID 30개가 포함됐다. 시간은 녹화별 길이를 한 번씩 합산한
  값으로 양손 시간을 중복 합산하지 않았다. DB 등록 전체나 아직 업로드되지 않은
  녹화까지 포함한 총계는 아니다.
- 원본 객체의 generation을 고정하고 다운로드한 메타데이터 8,037개와 incident
  파일 403개(553,044,174바이트)의 SHA-256을 재검증했다. 메타데이터 조회 후보
  8,050개 중 5 MB 초과 보고서 13개는 제외했으며 모두 0.9.12 녹화였다. 빈 JSON
  6개는 오류로 남겼다. 0.9.16 집계 대상 보고서에는 이 누락이 없다.
- 모든 대상 RAW와 카메라 타임스탬프 객체의 처음/마지막 8 KiB를 읽고, 녹화
  시작 `sync_point.monotonic_ns` 및 동일 host clock domain으로 끝 시각을
  비교했다. **전체 RAW 본문을 전수 검사한 것은 아니다.** 아래 대표 사례만
  양손 RAW와 카메라 타임스탬프 전체를 내려받아 모든 줄을 파싱했다. 영상 본문의
  화질·내용과 개별 촉각 센서의 압력 감도는 이번 검수 범위에 포함하지 않았다.
- incident는 tactile 스트림만 골라 실제 이벤트 시각이 녹화 구간 안인지 확인했다.
  카메라 재연결 로그와 중복 스냅샷을 장갑 실패 건수에 더하지 않았다. 사건의
  open–close 시간 전체를 연속 수신 중단 시간으로 취급하지 않았다.

51개 실패 녹화에는 Pi 10대와 물리 장갑 21개가 포함된다. 단일 장갑이나 단일

51개는 **이번 자료에서 확인한 수**이며 나머지가 무결함이라는 뜻도, 전체 장갑의
실패 확률이라는 뜻도 아니다. 5초는 끝 시각 불일치를 찾는 검수 기준일 뿐
제품의 허용 손실 기준이 아니다.

일반 보고서 512개의 수신 프레임 합계는 243,426,686개, 명시된 손실 합계는 785,057개다.
`lost / (frames + lost)`는 0.3215%지만, 완전히 멈춘 뒤의 누락이 포함되지 않을
수 있어 **실제 전체 누락률로 사용하면 안 된다.** 없는 loss 필드는 합산할 때
0으로 취급했으며, 검수 CSV의 `lost_samples_field_present`로 명시적 0과 구분했다.
예를 들어 9월 2일 `0960f6a9…`의 오른손은 214,858프레임 수신과 236,476개 손실을
보고했다(보고서 기준 52.395%). 이것만으로 그 손실의 원인을 FIFO로 확정하지 않는다.

복구 보고서 42개는 모두 `recovered.reason=interrupted_recording`이다.
이 보고서는 `frames` 대신 `frame_count`를 쓰고 원래 손실 카운터가 없어 위
손실률 계산에 섞지 않았다. 그중 4개에서 녹화 시간 안의 reader 실패와
15.703–59.464초의 촉각 후반부 누락을 추가 확인했다. 복구 원인 전체를 USB
실패로 단정하지 않는다. 복구 녹화 1개의 manifest는 빈 파일이어서 host 대조를
할 수 없었고, 그 녹화의 Pi는 session과 sync point의 일치로 확인했다.

첫 장갑의 8월 20일 녹화 `c3434714-e57c-418e-9078-3c11a845c8e3`에는
`no TAG packet for 5.1s and reconnect did not succeed within 15s`가 명시되어 있다.
해당 왼손 RAW보다 카메라 기록이 20.279초 더 길다. 새 세 번째 장갑의 과거 녹화에서는
reader 실패 로그를 찾지 못했으며, 그 장갑도 현장에서 완전 정지가 확인됐다고
말할 수는 없다. 과거 양수 손실 카운터가 있는 녹화는 8개였다.

세 번째 장갑은 동일 Pi USB 위치, 동일 reader 코드와 10 Hz 공백 명령으로
각각 300초를 요청했다. 두 번 모두 수신 정지와 USB IN `-EPROTO` 384개가
기록됐다. 관측기 손실은 0, 성공한 kernel IN 바이트와 userspace 수신 바이트는
일치했다. 시험 후 USB reset과 독립 readback으로 동일 MCU boot, 펌웨어, CONFIG,
저장 zero 보존을 확인했다. og-agent와 ModemManager는 원래 active 상태로
복구했고, 왼손 연결 상태와 녹화 경과 0을 확인했다. 펌웨어 쓰기는 하지 않았다.

세 장갑 모두 현재 실행한 정식 0.9.16 해시는
`b1c53157df9fc259a64ebe8a2c0454d916d2c2ccac163f083335496234345897`이다.

## 별도 데이터 무결성 문제와 관측 한계

- 대상 손별 RAW 1,107개 중 8개는 객체가 없고, 1개는 끝부분을 파싱할 수 없었다.
  정상적으로 처음/끝을 읽은 RAW는 1,098개였다. 누락 객체를 정상으로 계산하지 않았다.
- 9월 5일 `205fafd0…`의 오른손 RAW 끝에는 최소 65,536바이트의 NUL이 있고,
  같은 녹화의 카메라 타임스탬프 끝도 JSON 중간에서 잘려 있다. 파일 무결성 문제는
  확인됐지만 생성·저장·업로드 중 어디에서 발생했는지, FIFO와 관련 있는지는 미확정이다.
- 남아 있는 Loki 로그의 조회 범위는 9월 6–19일이었다. 8월 19일과 9월 2일의
  해당 시간대 조회는 비어 있었다. 따라서 그 사건은 업로드된 incident/session log로
  판단했다. 9월 12일에는 다른 Pi에서 `no TAG packet for 0.5s` 후 mute 복구를
  위한 OGLO USB reset 기록도 확인했으나, 녹화 안의 실패로 조인하지 않았으므로
  위 51개 집계에는 추가하지 않았다. enumeration의 `error -71`이나 카메라 reset을
  벤치의 OGLO bulk IN `-71`과 동일한 증거로 취급하지 않았다.
- 역사적 capture manifest의 SDK 버전과 현재 제안한 Python SDK rc4는 다르다.
  이 자료는 rc4 녹화의 실패 이력이 아니다. 또한 SDK의 실패 감지가 개선됐다는
  사실만으로 기존 펌웨어의 USB 동작이나 과거 기록이 복구되는 것은 아니다.
