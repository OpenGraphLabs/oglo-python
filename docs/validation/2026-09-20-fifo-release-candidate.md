## 추가로 발견하고 수정한 SDK 검사 문제

rc4의 일반 acceptance는 30초 수신을 마친 뒤 약 266ms 동안 샘플을 분석하면서
장갑의 스트림을 켜 둔 채 읽기를 멈췄다. 두 검사에서 수집된 구간의 순서는
연속이었지만 후속 상태에 장갑 내부 폐기 19개/22개, 처리 기한 초과 각 1회가
관측되어 FAIL했다. 이 실패 기록은 그대로 보존했다.

각 수집 작업이 끝나면 즉시 해당 장갑을 정지한 뒤 분석하도록 수정했다.
정지 전에 수신률·손실 카운터를 복사하여 실제 손실이 정지 과정에서 지워져
PASS로 바뀌지 않게 했다. 예외 시에도 해당 장갑을 정지한다.
같은 장갑·펌웨어에서 분석 시간은 약 266ms로 유지하면서 새 폐기·기한 초과는
모두 0으로 바뀌었다. 새 회귀 검사 3개는 기존 코드에서 실패하고 수정 후 통과한다.

수정한 SDK는 rc4와 구분되는 `0.1.0rc5`, 소스
`b320f5c68466248379f9be3fa96bb133197e49e2`이며 wheel SHA-256은
`291160a97f98f5a1d1249cf6dc602dacb9ffa2c3163dd1ced52a19beed98be36`이다.
이 wheel을 새 Pi 환경에 설치하여 일반 acceptance를 실행한 결과 **27 PASS / 4 SKIP**이다.
30초 스트림, RAW/CLEAN·임계값·속도 변경 및 원상복구, 60초 녹화·재생과
논리 재접속이 통과했다. 스트림과 녹화 각각의 새 내부 폐기·기한 초과는 0이다.
마지막 독립 readback도 원래 설정·zero·부팅·이미지가 같음을 확인했다.
Pi의 기존 og-agent/ModemManager 서비스와 usbmon의 원래 비활성 상태를 복구했다.

rc5 평가용 GitHub release는 미공개 draft로 준비했다. 업로드한 8개 asset을
다시 다운로드하여 원본 파일·ZIP 내부 7개 파일·모든 checksum과 대조했다.
rc4 draft에는 rc5로 대체됐음을 표시했고 이전 바이너리와 증거는 보존했다.
소스 PR은 아직 draft이며 main merge·정식 공개·NTU 발송은 하지 않았다.

## 오른손 R-00021의 동일 이미지 비교

OGLO-R-00021, USB `68EE8F495D30`에도 같은 Ubuntu 이미지를 썼다.
이 장갑의 정식 0.9.16은 같은 10 Hz 공백 명령 조건에서 각각 47.912초와
15.838초까지 수신한 뒤 멈췄고 USB IN 오류가 각 384건 발생했다.
쓰기 직전에도 원래 실행 해시와 기존 CONFIG·zero를 다시 확인했다.
쓰기 전후 NVS 20,480바이트는 동일하다
(SHA-256 `2252bb022d9e9e858d6259d299f8fb3559b0a91206cc1882359052fd27bb10b6`).
사용자의 USB 재연결 후 Ubuntu 실행 해시·새 MCU 부팅·설정·zero 보존을 확인했다.

| 검사 | 시간 | 촉각 / IMU / 자력계 프레임 | USB 오류 / 관측기 손실 |
| --- | --- | --- | --- |
| 10 Hz 공백 명령 | 300.012초 | 75,003 / 150,007 / 37,501 | 0 / 0 |
| 10 Hz LINK PING | 300.001초 | 75,000 / 150,000 / 37,500 | 0 / 0 |

두 검사 모두 순서 이상·시각 역행·헤더 이상·프레임 밖 데이터·새 내부 폐기·
새 처리 기한 초과가 0이다. 쓰기 재시도는 각각 152,021회·136,009회이며,
완전 프레임의 누락으로 이어지지 않았다.

정확한 rc5 wheel의 60.098초 녹화에서 저장된 샘플 52,580개
(15,022 / 30,046 / 7,512)의 값·순서·시각이 USB 원본과 모두 일치했다.
첫 대조 스크립트는 마지막 serial read가 패킷 중간에서 끝나는 경우를 처리하지
못해 실패했다. 마지막 133바이트 패킷의 앞 64바이트를 받은 직후 예정된 녹화
종료 명령이 나간 것을 확인하고, 유효한 마지막 미완성 패킷만 명시적으로
기록하는 별도 대조 스크립트로 검증했다. 완전히 수신한 프레임은 전부 비교했다.
원래 실패 로그·종료 코드·RAW는 수정하지 않았다. 이전 왼손의 완전 패킷 경계와
이번 오른손 경계를 통과하고, 내부 payload·header 변조와 잘못된 마지막 순서
번호는 실패시키는 5개 대조 검사도 통과했다. SDK 제품 코드는 바꾸지 않았다.

별도 일반 acceptance도 **27 PASS / 4 SKIP**이다. 30초 스트림, 설정 변경·복구,
60.069초 녹화·재생(15,015 / 30,032 / 7,508), 논리 재접속을 통과했다.
두 녹화와 스트림의 새 내부 폐기·처리 기한 초과는 모두 0이다.
마지막 독립 readback에서 MCU 부팅·이미지·CONFIG·zero 보존을 확인했고,
Pi 서비스 두 개를 원래대로 켜고 usbmon을 해제했다. 오른손 연결도 서비스에서
확인했으며 녹화는 실행 중이 아니다.

이로써 같은 Ubuntu 이미지의 단기 검증은 **서로 다른 왼손·오른손 두 대에서
각각** 통과했다. 양손 동시 검증은 아니다. 오른손 증거 archive SHA-256은
`fe90b7e5f9179c7a4e4babdb5fe5f6ffc67f9d803a300f8856d049e9ecdf42d1`이며,
원본 결과·대조 스크립트·NVS 백업을 포함한 파일 123개를 보존했다.
Mac으로 내려받은 archive와 내부 파일 123개를 각각 해시 검증했고,
저장된 전체 결과에 대한 판정도 Pi와 Mac에서 각각 통과했다.

## 업데이트 모드 전환에서 추가로 관측한 것

5분 검사 이후 Ubuntu 이미지로 바꾸기 위해 기존 도구의 `default_reset`을 실행하자
RTS 제어에서 `EPROTO (-71)`가 발생하고 운영체제에 ROM USB가 제때 나타나지 않았다.
이 시도에서는 플래시 쓰기가 시작되지 않았다. 이어 표준 USB GET_STATUS도
프로토콜 오류를 반환했다. 대상 장갑만 USB 버스 리셋하자 커널이
`device firmware changed`를 기록하고 같은 MAC의 Espressif ROM 장치로 다시 열거했다.

이는 업데이트 모드 전환/호스트 재인식 단계의 별도 관측이다. 데이터 수신 검사에서
같은 정지 현상이 재발했다고 단정할 수 없으며, 새 FIFO 코드가 모든 연결/전환 문제를
해결했다는 주장도 할 수 없다. 정확한 ROM MAC을 다시 검증한 뒤 Ubuntu 이미지
쓰기를 완료했다. 최종 업데이트 경로의 재현·개선 검증은 남은 항목이다.
이후 오른손의 정식 0.9.16→Ubuntu 0.9.17 전환은 추가 버스 리셋 없이
완료됐지만, 앞서 관측한 전환 문제가 일반적으로 해결됐다는 증거는 아니다.

## 추가로 연결한 L-00003의 기존 펌웨어 실패
