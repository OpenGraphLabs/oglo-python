# Linux/Pi USB comparison — 2026-09-19

> Historical validation record for the dated software and devices below.
> See [current candidate status](../08_candidate_status.md) before choosing a release.
> Raw `acceptance-results/` paths identify internally retained evidence, not public downloads.

**NO-GO for sustained capture: persistent USB reception failure also reproduced
on Linux, after approximately 442 seconds.** Linux recorded bulk-IN `-EPROTO`
errors while bulk-OUT keepalives completed. BLE sampling remained alive, and a
targeted USB bus reset restored communication without an MCU reboot. The exact
firmware/USB hardware cause remains unresolved. A separate, reproducible SDK
shutdown defect was corrected in commit `46f77a3`.

This follows the [Mac single-glove investigation](2026-09-19-usb-single.md).
The subsequent [matched PING comparison and diagnostic-image experiment](2026-09-19-usb-ping-ab.md)
records the next investigation phase separately.
The operator moved the same replacement glove to a Raspberry Pi and explicitly
confirmed that the cable also changed. This is a comparison of host/cable
combinations, not an isolated test of the operating system or USB driver.

## SDK-free 15-minute observation

The pyserial-only reader retained the Mac test's 8,192-byte reads, 50 ms read
timeout, 500 ms write timeout and separate 1 Hz LINK PING thread. It received
43,312,743 bytes over 900.024 seconds. All 901 ping writes succeeded, the final
STOP/status/identity/configuration/calibration queries worked, and MCU identity
was unchanged through those immediate postflight queries.

This was **not a lossless pass**. Independent decoding found one shared loss
interval: 13 tactile, 26 IMU and 6 magnetometer samples missing. The device drop
counter independently increased by exactly 45. The received counts were 225,001,
450,003 and 112,501 respectively. There were no malformed headers, unframed or
trailing bytes, backwards timestamps, read exceptions or command-write errors.

The host trace contains two long gaps before the next serial read, 242.505 ms and
296.281 ms. Both align with short device TX-stall/recovery records; the second
precedes the shared sequence gap. The device's second stall cleared with a
45-frame drop increment. Its nonblocking transmit queue holds 128 frames,
approximately 146 ms at the configured aggregate rate. Together these records
support temporary receive backpressure overflowing that queue. They do not
establish why the Python reader was descheduled or blocked: the diagnostic itself
wrote RAW and timing logs to the Pi's SD storage, and other setup/analysis work
also occurred during this run. This is distinct from the Mac's persistent silence
despite continuous userspace polling.

The full text usbmon trace captured all 901 ping submissions and matching
successful, full-length completions. It lost 561 diagnostic events overall, so it
must not be described as a complete USB trace. A later binary observer with a
1 MiB kernel ring captured 1,001,527 events without reported drops, including the
296 ms reader gap, the sample-loss interval and subsequent shutdown/reboot.
usbmon measures requests and completions at the driver/host-controller boundary;
it does not prove physical bus handshakes or MCU command parsing. See the
[kernel's usbmon documentation](https://docs.kernel.org/usb/usbmon.html).

## Reproduced shutdown defect and correction

After the SDK-free run had completed its successful immediate postflight queries
and closed the tty, the device restarted approximately eleven seconds later.
The kernel logged a USB disconnect and re-enumeration. The device journal recorded
a TX stall, a USB-wedge recovery event, then a software-reset boot. This happened
after the recording, not inside its 900-second capture window. The USB trace
contained no DTR-clear request at close. The initial tty's HUPCL flag was not
captured, so its value must not be asserted retrospectively.

A controlled comparison then isolated a condition that reproduces this failure:

| SDK and tty condition | Observed shutdown behavior |
| --- | --- |
| Original SDK; HUPCL enabled | 10-second record completed; close sent DTR clear; no subsequent disconnect in the observation window |
| Same original SDK; HUPCL explicitly disabled | 10-second record completed; close did not clear DTR; approximately eleven seconds later the firmware performed another USB-wedge recovery reboot |
| Corrected SDK; HUPCL explicitly disabled | 10-second record completed; explicit DTR clear observed; after a 20-second closed interval, queries confirmed the same MCU boot, firmware, CONFIG and calibration |

The old SDK assumed closing an owned descriptor would lower DTR and revoke the
firmware's sticky LINK PING authorization. That assumption depends on tty state.
Without a DTR-clear edge, an intentionally closed host can still look attached
to the firmware, which eventually interprets the undrained connection as a fault.
This is a demonstrated close/recovery-contract defect; it does not explain all
earlier mid-stream stalls.

Commit `46f77a3` explicitly lowers DTR after stopping the keepalive and performing
the existing STOP/drain handling, before closing an SDK-owned descriptor. It
preserves externally owned handles and their DTR state. Failure of a USB control
request still proceeds to descriptor cleanup. No RTS or firmware behavior changed.

The regressions reproduced two failures before the fix and pass afterward. The
full offline suites passed **495 tests on each of Python 3.10, 3.11, 3.12, 3.13 and
3.14**, with 11 physical tests deselected in each run. The Pi also passed all 495
offline tests against the installed corrected wheel, with the source checkout
excluded from pytest's import path. Wheel/sdist metadata checks also passed.
These automated results do not replace physical duration testing.

## Corrected SDK duration test

A requested 900-second recording failed with the corrected installed wheel and
HUPCL deliberately disabled. Recorder output stayed on SD storage; additional RAW
receive bytes and per-call traces went to tmpfs to reduce observer storage stalls.
The capture received data for 442.007 seconds and ended at 447.028 seconds after
the SDK's five-second silence guard fired for all three sensors. The partial
episode correctly records `complete=false` and the stream-stalled error.

The received prefix contained 110,490 tactile, 220,981 IMU and 55,245 magnetometer
samples, with zero sequence anomalies, backwards timestamps, malformed headers
or trailing bytes. Its 21,269,366 received bytes match the successful bulk-IN byte
count at the kernel boundary. This validates the saved prefix, not the requested
900-second recording.

An additional replay check independently decoded the captured USB payloads and
compared every saved sample's sequence, timestamp and sensor values. All matched;
the failed episode retained its incomplete/error metadata.

The reader continued polling: 8,468 reads included 99 empty reads after the last
data. Maximum read duration was 50.168 ms, inter-read host gap 70.118 ms, recorder
flush 33.366 ms and LINK PING interval 1.004460 seconds. No long userspace read
pause explains the persistent failure. The close-only SDK correction had not yet
executed when reception failed.

### USB boundary evidence

The binary observer captured 970,740 events with **zero reported observer drops**.
Analysis found no unmatched completions or overlapping submissions in the capture.

| Observation during capture | Result |
| --- | --- |
| Successful bulk-IN completions before failure | 479,696 |
| Largest gap between nonempty bulk-IN completions before failure | 4.028 ms |
| Bulk-IN failures after the last sensor data | 160 completions with `-71` (`EPROTO`), zero actual bytes |
| LINK PING bulk-OUT submissions/completions | 447/447 successful, full 10-byte completions, including after IN failed |
| USB disconnect or re-enumeration at failure | None |

The last successful IN completion was at host monotonic `2437546900 us`. The next
LINK PING completed at `2437547894 us`; the first IN error followed at
`2437548388 us`, 494 us later. This is a useful timing association, not proof that
LINK PING caused the fault. The observer measures driver/controller events, not
individual wire transactions.

After the capture window, the kernel also completed the STOP command in full,
although the userspace write eventually timed out. A subsequent plain-pyserial
GET STATUS probe received no response, despite a successful kernel OUT completion.
These distinctions matter: an OUT completion does not establish firmware command
consumption, and a userspace write timeout does not establish that no bytes left
the host.

Linux defines `EPROTO` broadly: bit-stuffing, missing response within bus turnaround
time, or another USB error the controller cannot distinguish. It cannot identify
a particular firmware bug, damaged component or cable by itself. See the
[kernel USB error definitions](https://docs.kernel.org/driver-api/usb/error-codes.html).

### Live failed-state probes and recovery

Before reset, a standard USB device GET_STATUS completed in 2.4 ms. Endpoint
GET_STATUS requests were rejected locally with `EBUSY` while `cdc_acm` owned the
interfaces; they provide **no endpoint HALT result**. No driver detach was used
for those probes.

The same glove answered BLE identity and CONFIG reads and delivered 31 sensor
notifications containing 93 decoded samples. Their sequence numbers and device
timestamps advanced strictly, spanning 2.3 seconds of device time. Firmware source
places these samples in the main scan loop; the observation rules out a complete
MCU/scan-loop freeze during that probe. It is not a BLE throughput qualification.
The BLE status characteristic was empty and supplied no additional status evidence.

A targeted `USBDEVFS_RESET` of this glove succeeded. Immediately afterward, USB
STATUS/IDENT/CONFIG/ZERO queries all answered. MCU boot identity and boot counter
were unchanged; firmware hash, CONFIG and calibration matched. No power cycle or
firmware update was needed. This demonstrates recovery by reinitializing the USB
path, not whether its initiating defect lies in device firmware, USB electrical
behavior or host/device interaction.

The recovered device journal was complete: 8,491 records, zero journal queue drops.
It records a TX stall at device uptime 856,396 ms, approximately 106 ms after the
last IMU timestamp (856,290.314 ms). By the DTR-clear event at 865,619 ms, its
drop counter had increased from zero to 4,286. A later TX-stall-clear event must
not be mistaken for restored host reception: only the targeted USB reset restored
the observed command/reply path. No MCU reboot occurred across this incident.

After recovery, the host HUPCL setting was confirmed enabled and a fresh
10-second SDK recording completed. Its saved samples matched the captured USB
bytes. After a further 20 seconds with the port closed, queries confirmed the
same MCU boot, firmware, configuration and calibration. This is a recovery check,
not a substitute for the failed duration gate.

## Conclusion and next isolation gate

The sustained failure is reproducible across Mac and Linux host/cable combinations.
A Mac-only driver defect, SDK parser/recorder failure, or complete MCU freeze
cannot explain all the observations. The Linux IN-error incident and the earlier
Mac SDK-free OUT-delivery incident are distinct signatures; a shared initiating
defect has not been proved.

The remaining boundary is the device USB implementation/electrical link and its
interaction with the host controller. The next discriminating test should capture
USB wire traffic and device endpoint/DMA state at the first failure, with power
and D+/D- integrity measured under the same load. A controlled firmware A/B that
changes only the USB stack/endpoint handling, preserving the same host, cable and
glove, can then test a specific software hypothesis. A successful bus reset alone
does not justify assigning firmware-versus-hardware probabilities.
