# OGLO USB·SDK 실험 종합 — 2026-09-19~22

> Historical validation record for the dated software and devices below.
> See [current candidate status](../08_candidate_status.md) before choosing a release.
> Raw `acceptance-results/` paths identify internally retained evidence, not public downloads.

**확인한 핵심 결함은 펌웨어의 USB FIFO 배정 오류와 SDK의 동기 저장에 따른 수신 지연이다.**
둘을 수정한 canonical 0.9.17 + SDK rc7 조합에서 Linux·Mac 양손 75분 녹화,
문제 보고 장갑 두 대의 Pi 8시간 59분 33초 연속 녹화가 샘플 누락 없이 완료됐다.
초기 상태 조회 timeout, 일부 연결/업데이트 전환, 물리 재연결 반복 검증은 남았다.
모든 과거 끊김의 원인 또는 모든 장갑의 신뢰성을 확정한 결과는 아니다.

이 문서는 9월 22일 완료한 증거 검수를 기준으로 기존 실험을 통합한다.
새 스트림·펌웨어 쓰기·장치 리셋을 실행하지 않았다. 원본 실패 판정은 변경하지 않는다.
이전 문서의 “현재/미완료”는 해당 시점 기록이며, 아래에 후속 결과를 연결했다.

## 실제로 고친 내용과 근거

**펌웨어:** USB endpoint 4가 FIFO 1을 사용하도록 선택돼 있는데, 버퍼 배정은
endpoint 번호를 기준으로 다른 FIFO 레지스터에 쓰고 있었다. 실제 장갑의 레지스터,
진단 ELF, 배포된 정식 0.9.16 바이너리에서 불일치를 확인했다. 0.9.17은 선택한
FIFO 번호에 맞춰 배정하고 알림 endpoint의 배정도 처리한다. “관찰→수정 개입→
정식 복구 후 재발”과 여러 장갑의 수정 전후 비교가 근거다. 전기적 파형 측정은 하지 않았다.

**SDK 저장:** 데이터 수신 작업이 파일 쓰기·fsync까지 기다리던 구조를 rc7에서
별도 저장 작업으로 분리했다. 대기 chunk는 8개로 제한하고 저장 오류/대기열 초과를
정상 녹화로 숨기지 않는다. 자연 발생 fsync 지연 계측과 동일 지연 주입 대조가 근거다.

**SDK 종료·실패 처리:** DTR을 명시적으로 해제하지 않아 종료 뒤 장갑이 호스트
연결 상태를 잘못 유지하는 경우, Mac `tcdrain()` 무한 대기, 실패한 쓰기 뒤 후속
명령 전송, 한 손 실패 후 상대 녹화가 남는 경우 등을 수정했다. 5초 수신 정지 감지,
불완전 녹화 보존, 설정 복원과 단독/양손 검사 범위도 보완했다.
0.9.16 이후의 `tag_short_writes` 재시도 횟수를 실제 샘플 폐기와 구분했다.

**현장 수집 보고:** 촉각 데이터가 먼저 멈췄어도 `completed`로 표시된 사례를
확인했다. USB reader 최종 실패를 partial/failed로 보존하도록 수집기·품질 판정
수정안을 준비했다. 코드·테스트 결과와 현장 배포·실제 현장 재검증은 구분한다.

자동 테스트는 후보 시점 rc7 Mac 526개, Pi 509개 통과 및 선택 모듈 1개 제외,
CI 18개 작업 통과로 기록돼 있다. 이것을 실기기 시간이나 센서 정확도 검증에 합산하지 않는다.

**업데이터:** 9월 21일 동일 0.9.17 후보의 정식 키 서명과 감독하 시험용 선택지를
`oglo-updater.vercel.app`에 배포했다. 업데이터 70개 테스트와 CI, 운영 UI의 선택지를
확인했다. 이것은 웹앱·서명 배포의 완료이며, 브라우저로 실제 장갑에 설치한 뒤
동작·복구까지 확인한 실험은 아직 아니다.

## 현장 자료에서 확인한 범위

대상은 0.9.16이라고 저장된 업로드 녹화이며 Pi 10대·물리 장갑 30개를 포함한다.
reader 실패 51개에는 물리 장갑 21개가 포함됐다. 554개 전부의 RAW 본문을
전수 디코딩한 것은 아니다. 메타데이터·incident·RAW와 카메라의 처음/끝을 대조했고,
대표 사례는 전체 본문을 읽었다. 저장된 버전 표기는 당시 바이너리 해시 확인의 대체가 아니다.

대표 8월 19일 OGPI-004 녹화에서는 촉각이 왼손 47.268초, 오른손 49.799초에
끝났지만 카메라 시각 기록은 316.520초까지 이어졌다. 보고서의 completed만으로
이를 정상 녹화로 취급하면 안 된다. 과거 데이터의 유효 구간 판정은 별도 과제이며
원본 GCS 객체나 DB 판정은 이번 조사에서 수정하지 않았다.

샘플 수와 첫/마지막 시각으로 주파수를 계산했으며, 설정값만 보고 판정하지 않았다.
원본 압축본과 내부 95개 파일은 Mac에 저장하고 해시를 검증했다.

이는 전송·저장 스트림의 빈도와 연속성이다. 센서 내부에서 매 프레임마다 새로운 물리
측정이 이뤄졌는지, 센서 정확도, 압력 환산, 지연 0, 양손의 하드웨어 동기화까지
검증한 것은 아니다. 장갑의 wrap을 푼 시계와 호스트 수신 시각을 구분해 분석했다.

## 현재 결론과 남은 검증

| 질문 | 증거로 말할 수 있는 범위 |

| 수정 후 장시간 스트림은 확인했나? | **확인했다.** 위 두 조합의 호스트·버전·시간 조건에서 완료했다 |
| 모든 과거 실패가 같은 원인인가? | **미확정.** 명령 입력 실패, 시작 timeout, 현장 사건, 낙하/이동 사건은 별도다 |
| 양손 Mac 8~9시간도 했나? | **아니다.** Mac 최장 완료 양손 연속 검증은 이 기록에서 75분이다 |
| 출하 전체/NTU 정식 전달 승인인가? | **아니다.** 개별 조건의 통과를 전체 무결점 승인으로 확장하지 않는다 |

우선 남은 것은 (1) 대기 후 GET STATUS timeout의 재현과 원인 분리,
(2) Pi 직접 수신 도구의 저장/로그 지연을 분리한 동일 30분 비교,
(3) 문제 보고 조건인 20~30분 수신 후 물리 분리·재연결 반복,
(4) 실제 웹 업데이터 설치·복구 경로 검증이다. 센서 기능·정확도와 현장 Agent 전체
수집·업로드는 별도 검증 범위다. 업데이터의 0.9.17 선택지·서명·배포 완료와
실제 장갑의 웹 업데이트 성공은 서로 다른 단계다.
