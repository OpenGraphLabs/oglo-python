# SDK 내장 펌웨어 업데이트 UX 계획

2026-09-23. **설계안이며 아직 구현·배포되지 않았다.** 이 문서는 연구자가 보유한
0.9.16 장갑 20쌍을 별도 웹 업데이트 창 없이 관리하기 위한 계획이다.
실기기 업데이트, 배포 정책 변경, 연구자 PC 설치는 수행하지 않았다.

## 1. 제품 결정

- 연구자는 SDK 설치/교체와 해당 랩의 업데이트 정책 적용을 처음 한 번 수행한다.
  설치 안내에서 한 과정으로 제공하고, 이후 장갑마다 승인·포트 선택·버전 선택을 요구하지 않는다.
- 기존 `connect()` / `connect_pair()` 사용 흐름에 수집 전 준비 단계를 통합한다.
  일반 SDK 기본 설정은 펌웨어를 쓰지 않는다. 이 랩에서 한 번 켠 정책만 자동 쓰기를 허용한다.
- 정책은 검증한 0.9.17의 서명된 정확한 이미지를 고정한다. `latest`를 따라가거나
  향후 SDK 업데이트만으로 목표 펌웨어가 바뀌게 하지 않는다.
- 대상은 해당 호출이 선택한 장갑이다. 검색 중 우연히 발견한 다른 장갑을 업데이트하지 않는다.
- 연구자는 평소처럼 장갑을 USB로 연결하고 수집 코드를 실행한다. 장갑을 연결만 해둔
  상태에서 SDK 프로세스가 실행되지 않으면 업데이트는 진행되지 않는다.
- 업데이트는 수집 전 단계에서만 수행한다. 녹화 시간은 양손 준비가 끝난 뒤부터 잰다.
- 별도 앱·상시 백그라운드 서비스·SSH를 필수로 만들지 않는다.

## 2. 최초 한 번의 준비

우리 쪽 작업:

1. USB 응용 프로그램 업데이트 기능을 SDK에 구현한다. 일반 스트리밍 연결에
   `FW` 명령을 허용하는 방식이 아니라, 독립적인 업데이트 세션을 내부에서 관리한다.
2. 서명된 펌웨어·manifest·검증 키와 랩 정책을 승인된 배포 경로로 제공한다.
   패키지에 포함하거나 사전 캐시해, 정상 사용 때 매 장갑마다 웹 로그인하지 않게 한다.
   기존 배포 권한/장비 할당 정책을 존중하며 공용 관리자 자격 증명을 SDK에 넣지 않는다.
3. 실제 0.9.16→0.9.17 USB 업데이트·자동 재부팅·재연결·설정 보존을 물리 장갑에서 검증한다.
4. SDK 버전, 펌웨어 해시, 정책 파일, 설치 절차를 한 배포 묶음으로 고정한다.

연구자/랩 관리자 작업:

- 현재 수집 프로세스를 종료하고, 안내된 SDK 버전과 랩 정책을 한 번 설치한다.
- 설치 확인은 현재 Python 환경에서 수행한다. 다른 가상환경에 설치해 구 SDK가
  계속 실행되는 경우를 감지하고 실제 import 경로·버전을 기록한다.
- 이후 기존 한 쌍 수집 코드는 그대로 사용한다. 여러 쌍이 동시에 연결되어 있다면
  사용할 두 장갑의 serial을 지정하는 설정이 필요하다. 임의로 두 대를 골라 연결하지 않는다.

아래 터미널 문구와 추가 CLI/API는 모두 설계 예시이며 현재 존재하는 명령이 아니다.

## 3. 처음 사용하는 0.9.16 한 쌍

사용자 동작: 장갑 연결 → 기존 수집 코드 실행 → 준비가 끝날 때까지 기다림.

터미널 예시:

```text
OGLO: 장갑을 준비하고 있습니다. USB 연결을 유지해 주세요.
왼손 L-00067: 0.9.16 → 0.9.17 적용 중 … 64%
오른손 R-00065: 대기 중
OGLO: 양손 업데이트와 설정 보존 확인 완료. 수집을 시작합니다.
```

SDK 내부 순서:

1. USB descriptor로 후보를 찾고, **첫 STOP/GET 명령 전에** 다른 수집기/뷰어의 점유를
   확인하고 후보 장치의 소유권을 확보한다. 프로세스 간 장치 신원 잠금과 호스트별
   USB/tty 점유 방식을 검증한다. `lsof` 확인이나 `exclusive=True` 하나만으로
   모든 프로그램과의 배타성을 보장한다고 가정하지 않는다.
2. 확보한 세션에서 논리 serial/side, 업데이트 기능, 현재 이미지, 설정과 보정값을
   읽고 저장한다. 두 대상 모두 식별·정책·준비 조건을 확인한 뒤 쓰기를 시작한다.
   검색 중 확인한 비대상 장갑에는 펌웨어를 쓰지 않는다. 다른 프로그램을 강제로 종료하지 않는다.
3. 장갑 하나씩 서명 검증 가능한 응용 프로그램 이미지를 전송한다.
   기본 모드는 순차 처리이며, 동시 쓰기는 별도 실기기 검증 전 도입하지 않는다.
4. 자동 재부팅 후 같은 USB 신원을 다시 찾아 실행 이미지 해시를 확인한다.
   포트 경로가 바뀌어도 다른 장갑으로 대체하지 않는다.
5. serial/side/pair/batch 및 보정·설정이 보존됐는지 확인한다. 자동 재보정은 하지 않는다.
6. 양손의 USB 명령 응답과 tactile/IMU/mag 기본 수신을 확인하고 사용자에게 반환한다.
   이 기본 점검을 장시간 안정성 또는 물리 센서 품질 합격이라고 표시하지 않는다.

진행률은 실제로 확인된 전송량을 사용한다. 재부팅·재연결·검증 단계는 별도 상태다.
전송 100%만으로 업데이트 완료를 표시하지 않는다. 소요 시간은 실제 측정 후 안내하며,
기존 6/10초 연결 timeout을 업데이트 전체에 그대로 적용하지 않는다.

## 4. 이미 업데이트된 한 쌍

```text
OGLO: 양손 준비 완료 — 0.9.17. 수집을 시작합니다.
```

- 실제 실행 해시와 신원을 다시 확인하고 같은 이미지라면 쓰기를 건너뛴다.
- 다른 PC에서 이미 업데이트한 장갑도 다시 쓰지 않는다.
- 로컬 성공 이력만으로 확인을 생략하지 않는다. 반대로 로컬 이력이 없다는 이유로
  같은 이미지를 재설치하지 않는다.
- 매 사용 때 장시간 검사를 반복하지 않는다. 연결 확인과 첫 설치 후 검사는 구분한다.
- 시작 지연은 준비 단계로 기록하고 녹화 기간에 합산하지 않는다.

## 5. 실패했을 때

| 상황 | 자동 동작 | 연구자에게 보이는 안내 |
| --- | --- | --- |
| 한쪽을 연결하지 않음 | 쓰기 전 대상 확인 단계에서 중단 | `오른손 R-xxxxx를 연결해 주세요.` |
| 다른 프로그램이 장갑 사용 중 | 임의 종료/쓰기 없이 중단 | `장갑을 사용 중인 프로그램을 종료한 뒤 다시 실행해 주세요.` |
| 전송 중 케이블 분리 | 실패 단계와 대상 기록, 양손 수집 시작 보류 | `L-00067 연결이 끊겼습니다. 다시 연결한 뒤 실행해 주세요.` |
| 쓰기 완료 여부가 모호함 | 재접속 후 실제 이미지부터 검사 | `장갑의 업데이트 결과를 확인하고 있습니다.` |
| 왼손 완료·오른손 실패 | 왼손 성공 이력 보존, 양손 준비 실패 반환 | `오른손 준비가 완료되지 않아 수집을 시작하지 않았습니다.` |
| 장갑이 계속 무응답 | 제한된 재접속 후 자동 반복 중단 | `R-00065의 USB를 다시 연결한 뒤 실행해 주세요.` |
| 설정/보정 불일치 | 원본과 차이 보존, 해당 장갑 수집 차단 | `L-00067 설정 확인이 필요합니다. 진단 기록을 담당자에게 전달해 주세요.` |
| 목표와 다른 실행 이미지 | 정책에 따라 명시적으로 중단 | `이 장갑은 랩에서 지정한 펌웨어와 다릅니다.` |

- 다음 실행에서는 실제 장갑 상태를 재확인한다. 완료한 왼손은 재설치하지 않고
  오른손만 처리할 수 있어야 한다. 중단된 임의 바이트 위치에서 무조건 이어 쓰지는 않는다.
- 실패했다고 기존 정상 장갑까지 자동 다운그레이드하지 않는다. rollback 지원과
  실제 복구 상태를 확인하며, 지원되지 않는 복구는 담당자 조치로 남긴다.
- pair 준비 실패 시 정상 `Glove` 쌍을 반환하지 않는다. 사용자가 요청하지 않은
  한 손 녹화나 서로 다른 정책 상태의 양손 녹화를 시작하지 않는다.
- Ctrl+C는 요청 즉시 취소 의사를 접수하고 프로토콜상 가능한 안전한 경계에서 종료한다.
  종료/프로세스 강제 종료 뒤의 상태는 다음 실행에서 검증한다.
- 입력을 요구하는 팝업·브라우저·`stdin` 질문은 없다. 상세 예외와 결과 파일을 제공하고,
  사람의 조작이 필요한 경우 해당 장갑 번호와 다음 행동 하나를 보여준다.

## 6. 20쌍을 운영하는 방법

- 평소 사용하는 한 쌍부터 준비한다. 새로운 장갑을 사용하는 날 같은 절차로 처리된다.
  이는 40대를 모두 업데이트했다는 뜻이 아니다.
- 전체 40대를 사용 전 끝내야 하면 SDK에 같은 엔진을 사용하는 일괄 준비 명령을
  추가한다. 한 번 실행한 뒤 연결 가능한 수만큼 장갑을 교체하면 순차 처리한다.
  별도 앱이나 장갑별 승인 창은 열지 않는다.
- 일괄 모드는 업데이트 대상 목록/랩 정책을 명시적으로 사용한다. 일반 `connect_pair()`가
  연결된 40대 전부를 변경하는 동작은 하지 않는다.
- 받은 40대의 serial 목록과 대조해 `검증 완료 / 실패·확인 필요 / 아직 연결 안 됨`을 집계한다.
  실제로 연결한 두 대만 성공했다고 전체 40대 완료로 표시하지 않는다.
- 여러 PC의 결과는 내보내기 파일로 합칠 수 있게 하고, 장갑 신원·실제 해시·검증 시각으로
  중복을 제거한다. 서버 업로드가 필요한 경우 별도 승인된 연결을 사용한다.

## 7. SDK 구현 범위

- 연결 전 준비 단계: 정책 로드, 명확한 대상 선택, 준비 상태/진행 이벤트, 단계별 기한.
- 서명 패키지 처리: 고정된 이미지·manifest·signature·허용 하드웨어·캐시 확인.
- USB 업데이트 세션: 일반 keepalive/streaming과 분리, 배타적 소유권, 전송 및 명령 처리.
- 재접속/후검증: 같은 장갑 재식별, 실제 실행 해시, 설정·보정 보존, 기본 수신.
- 영속 이력: 시도 ID, serial/USB ID, 이전/목표/실행 해시, SDK/정책 버전, 실제 시간,
  전송/재부팅/검증 상태, 실패 이유, 설정 비교와 진단 파일.
- 출력: 터미널에는 간결한 준비 상태, 프로그램에는 구조화된 진행 이벤트와 예외.
  사람이 입력하지 않는 실행에서도 무한 대기 없이 성공/실패를 구분한다.
- 녹화 메타데이터: 실제 실행 펌웨어 해시와 SDK/정책 버전. 다음 SDK 설치가 기존 실험의
  펌웨어 목표를 임의로 바꾸지 않게 한다.

현재 SDK는 스트리밍 연결의 `FW` 명령을 거부한다. keepalive가 업데이트 바이너리에
끼어드는 것을 막는 제약이므로 삭제하지 않고 내부 전용 세션을 추가한다.
현재 `connect_pair()`는 두 대 초과 연결 시 거부하므로, 여러 쌍 지원에는 명시적
대상 선택을 추가해야 한다. 여기서 제안한 자동 준비/일괄 준비는 현재 구현에 없다.

## 8. 검증과 배포 순서

1. SDK 오프라인 검사: 대상/정책 혼동, 서명·해시 오류, 부분 전송, COMMIT 응답 유실,
   포트 변경, 동시 실행, 취소, 손상된 이력, 설정 불일치, 한쪽 실패, 재시도.
2. 보유 장갑에서 실제 **USB 응용 프로그램 업데이트 경로** 검증. 기존 ROM 쓰기 검사로
   대체하지 않는다. 재부팅과 설정 보존, 재실행 시 불필요한 쓰기 방지도 확인한다.
3. Ubuntu PC와 Zed box의 실제 OS/아키텍처·USB 권한·Python 환경에서 설치/동작 확인.
   Mac 지원도 해당 호스트에서 별도로 검증한다.
4. 연구실의 R-00065/L-00067 한 쌍에 먼저 적용하고, 반복 수신 및 실제 연속 장시간
   검사를 완료한다. 기본 준비 확인을 이 단계의 대체물로 쓰지 않는다.
5. 같은 SDK·서명 이미지·정책으로 나머지 38대를 처리하고 40대 완료 목록을 확인한다.

배포 조건: 별도 업데이트 창·장갑별 승인 없이 동작하고, 실제 후검증 이전에는 완료로
표시하지 않으며, 중단/실패를 정상 수집 시간으로 보고하지 않아야 한다.

## 9. 코드 검토로 추가한 필수 조건 — 2026-09-23

상세 근거: [구현 전 코드 검토](2026-09-23-sdk-update-preimplementation-audit.md).
아래는 구현 요구사항이며 현재 SDK에 적용됐다는 뜻이 아니다.

- **0.9.16 수신 상태 복구:** 바이너리 수신 중 텍스트 `FW ABORT`는 실행되지 않고,
  잘못된 명령 바이트도 60초 무수신 타이머를 갱신한다. 중단됐을 수 있는 세션에는
  `GET CONFIG`/STOP/LINK PING을 반복 전송하지 않는다. 이전 쓰기 작업이 끝나고 더 이상
  OUT 바이트를 보내지 않는 것이 확보된 뒤, 예를 들어 65초의 무송신 정리 시간을 적용하고
  제한된 재확인을 한다. 이 시간은 재시작한 프로세스에서도 장치별 이력으로 처리한다.
  이는 프로토콜 대기 상태 복구이며 USB 스택 자체의 먹통 복구를 보장하지 않는다.
- **시작부터 영속 기록:** `FW BEGIN`도 inactive slot erase를 시작할 수 있다.
  READY를 못 받았더라도 부작용 없는 실패로 간주하지 않도록 BEGIN 전에 기록한다.
- **I/O 전체 제한 시간:** open/write/read/abort/close/rebind에 기한을 둔다.
  응답 읽기 timeout만으로 충분하지 않다. timeout 이후에도 살아 있는 쓰기 작업을
  남겨 둔 채 새 세션을 만들지 않는다. 취소 불가능한 OS 호출은 격리된 작업 프로세스와
  상태 재검증으로 다루고, 정리가 증명되지 않으면 자동 쓰기를 중단한다.
- **재부팅 중 소유권 유지:** tty 경로가 바뀌어도 물리 USB 신원에 묶은 잠금을 유지한다.
  다음 프로세스가 일반 handshake부터 실행해 진행 중 업데이트를 방해하지 않게 한다.
- **전송 해시와 실행 해시 분리:** 전체 파일 SHA-256은 다운로드/전송 검증에,
  ESP 실행 이미지 digest는 `GET FWINFO` 후검증에 사용한다. 둘의 대응은 서명된
  배포 자료 또는 검증된 이미지 파싱으로 묶는다.
- **같은 버전·다른 해시:** 기존 updater는 같은 버전 재설치도 거부한다. 시험 이미지와
  정식 이미지가 모두 0.9.17이면 자동 덮어쓰기/다운그레이드 대신 담당자 확인 상태로 둔다.
- **보존 항목을 명시:** identity/GET ZERO 외에 노출된 영속 설정을 목록화한다.
  재부팅하면 사라지는 런타임 설정과 읽어 확인할 수 없는 IMU 설정은 별도로 처리한다.
  확인하지 않은 항목까지 '전체 설정 보존'이라고 표시하지 않는다.
- **승인된 배포 경로:** 웹의 로그인·station 권한·60초 서명 URL을 SDK가 그대로
  무인 사용한다고 가정하지 않는다. 첫 버전은 승인된 서명 묶음과 고정 랩 정책을
  사전 제공하는 경로를 우선 구현하고, 서버 설치 이력 연계는 별도 인터페이스로 정의한다.
- **완료 기록:** 현재 SDK 녹화 meta에는 실행 해시/정책 버전이 없다. 연결 후 검증 결과를
  녹화 시작 스냅샷에 넣고, 이후 replay에서도 해당 출처를 보존한다.
- **연속성 표시:** 캐시된 `rates_seen`이나 도착했던 구간의 평균만으로 현재 정상 수신을
  판단하지 않는다. 모달리티별 마지막 수신 시각과 전체 측정 창의 앞·뒤 공백을 검사한다.
- **기존 SDK 보수:** 긴 episode 재생의 반복 전체 배열 계산, 정지 후 오래된 Hz 표시,
  양손 예제의 한쪽 실패 전달 지연을 수정하고 회귀 검사를 추가한다.

추가 시험에는 READY 유실, 중간 수신 중 취소/프로세스 종료, 60초 전 재실행,
마지막 ACK 유실, COMMIT 유실, 쓰기/close 무응답, 두 프로세스 충돌,
USB 포트 번호 교체, 한 손만 완료, 동일 버전 다른 이미지, 오프라인 재시작이 포함된다.
원래 0.9.16 장갑으로 시작하는 실제 USB 업데이트·자동 부팅·보존 검사는 여전히 배포 전 필수다.
